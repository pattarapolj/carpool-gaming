# API and behavior contracts

**Purpose:** Own requests, responses, error codes, observable state guarantees and live-event behavior for the MVP. Sections 1–7 explain create game in detail; sections 8–9 cover the remaining operations and events. No application or test implementation is included.

**Status:** Existing specified behavior consolidated from the previous design documents. Unresolved decisions remain explicitly pending. Required behavior is not a claim of implementation.
[Product requirements](product.md) define the need; [LLD](lld.md) defines implementation responsibilities; [test specification](../testing/test-spec.md) defines verification.
**Scope:** A shared schema expresses field rules; it does not replace this behavioral agreement.

## Common request and error behavior

Every authenticated request uses `Authorization: Bearer <opaque token>`. Raw host/captain tokens are generated with `crypto.randomBytes(32)` and returned only at creation/join time. PostgreSQL stores their SHA-256 hashes.

### Validation and error envelope

- Write routes accept only `Content-Type: application/json`; malformed JSON returns `400`.
- Requests are validated with shared Zod schemas. Correct JSON with invalid values returns `422`.
- Authentication runs before resource authorization. A missing, invalid, or expired token returns `401`; a valid token without permission for the requested game/action returns `403`.
- Every error uses this envelope. `requestId` is generated by the server and is safe to show to support; it must not contain a token, answer key, or database error.

```json
{
  "error": {
    "code": "ANSWER_ALREADY_LOCKED",
    "message": "This car has already locked an answer.",
    "requestId": "req_01J…"
  }
}
```

| HTTP status | Meaning | When used |
|---|---|---|
| `400` | `MALFORMED_JSON` | Request body cannot be parsed as JSON. |
| `401` | `UNAUTHENTICATED` | A protected route has no valid bearer token. |
| `403` | `FORBIDDEN` or `CAPTAIN_REQUIRED` | Valid token belongs to another game or has the wrong role. |
| `404` | `GAME_NOT_FOUND` or `ROUND_NOT_FOUND` | The requested ID/code does not exist. |
| `409` | State conflict | Duplicate name/answer, already started game, closed game, or team already left. |
| `422` | `VALIDATION_ERROR`, `GAME_NOT_READY`, or `ROUND_EXPIRED` | JSON is valid but field values, game readiness, answer value, or deadline are invalid. |
| `500` | `INTERNAL_ERROR` | Unexpected fault; log the cause server-side and return only a generic message. |

## 1. What “contract” means here

A contract is the agreement between the caller and your application:

- **The caller supplies:** a request with the required inputs.
- **Your application guarantees:** the documented response and state change when the request succeeds.
- **When it cannot succeed:** your application returns the documented error.

For this feature, the browser needs to know what to send and what to expect, while the API must produce that result. Tests check the same agreement. The contract does not prescribe the names of internal functions or how files are split.

The **contract defines the rule**, the **catalog lists cases that exercise it**, and the **test checks the actual result**. A future shared schema in `packages/contracts` can express field shapes and validation, but it cannot by itself prove persistence, authorization or other behavior.

## 2. Operation and inputs

| Item | Agreement |
|---|---|
| User intention | A host creates a private lobby to share with other cars. |
| Method and path | `POST /v1/games` |
| Authentication | None required; this operation issues the host credential. |
| Content type | `application/json` |
| Request | An object containing `name` and `roundIntervalSeconds`. |

| Field | Required | Accepted value | Normalization |
|---|---|---|---|
| `name` | Yes | String with 1–60 characters after trimming surrounding whitespace. | Remove surrounding whitespace before validating length and returning/storing the name. |
| `roundIntervalSeconds` | Yes | A JSON number equal to `300`, `600` or `900`. | Do not convert a string such as `"300"` into a number. |

Both fields are required. The UI's default five-minute selection means the UI supplies `300`; it does not imply that the API accepts a missing interval.

Example inputs: name **Beach convoy**, interval **300**. For a normalization case, supply the same name with two spaces before and after it. The resulting name must be **Beach convoy**.

## 3. Success guarantees

A valid request returns HTTP **201** with these fields:

| Response field | Required value |
|---|---|
| `game.id` | The created game's generated UUID, represented as a string. |
| `game.name` | The validated, trimmed name. |
| `game.joinCode` | Six characters, each an uppercase ASCII letter A–Z or digit 0–9; unique among stored game join codes. |
| `game.status` | Exactly `LOBBY`. |
| `hostToken` | The generated raw opaque host credential, represented as a nonempty string. |

Generated identifiers and credentials vary. Assert their documented properties and relationships; do not expect one particular generated value. A sample join code is an illustration, not a constant to return.

This contract does not define an exact allowlist of every public response field. Check required fields and forbidden credential fields; settle additional public fields with your teammate before adding exact whole-response assertions.

### State and credential guarantees

| ID | Required behavior | Evidence your tests/review should establish |
|---|---|---|
| CG-01 | A valid request creates a durable lobby with the supplied interval and normalized name. | Successful HTTP result corresponds to the game stored in the test database. |
| CG-02 | Stored join codes are unique. | A database constraint prevents two games from storing the same code. Randomly creating two different codes alone does not prove this guarantee. |
| CG-03 | The response provides the host credential for this game. | A nonempty raw token is returned; the stored hash corresponds to that token and game. |
| CG-04 | Storage contains the token's SHA-256 hash, not the raw token. | A database-backed test verifies the storage contract; review token generation against the cryptographic requirement above. |
| CG-05 | The public response does not disclose stored token hashes. | Inspect response fields independently of the database assertions. |

The raw credential is issued by creation; later snapshots must not expose it. Its presence here does not define a retry/replay protocol for repeated create requests.

## 4. Failure guarantees

| ID | Situation | HTTP status | `error.code` |
|---|---|---|---|
| CG-06 | A JSON request body cannot be parsed because its syntax is broken. | `400` | `MALFORMED_JSON` |
| CG-07 | The body is valid JSON, but required field values fail the rules in section 2. | `422` | `VALIDATION_ERROR` |
| CG-08 | An unexpected creation/persistence failure occurs, including exhausted join-code creation attempts. | `500` | `INTERNAL_ERROR` |

Each error response has an `error` object containing:

| Field | Agreement |
|---|---|
| `error.code` | The stable machine-readable code from the table. |
| `error.message` | A human-readable description; unexpected failures use a generic message. Exact wording is not specified. |
| `error.requestId` | A nonempty server-generated request identifier. Exact format is not specified. |

Error responses must not disclose stack traces, SQL, raw credentials, token hashes or answer-key data. Tests should not depend on an unspecified exact message or request-ID format.

For malformed JSON, send an actually broken JSON body with the agreed content type. Sending a valid object whose interval is the string `"300"` exercises **CG-07**, not **CG-06**.

## 5. Examples to turn into your own tests

Except where stated, use a valid name and an interval of `300` so each case isolates one condition. Start with a case that already exists in your test file and improve it rather than duplicating it.

| Case | Changed input or situation | Expected outcome | Rule |
|---|---|---|---|
| Normal creation | Name Beach convoy; interval 300. | `201`; required response fields and matching persisted lobby. | CG-01, CG-03 |
| Name normalization | Surround the valid name with whitespace. | `201`; returned and stored name are trimmed. | CG-01 |
| Minimum name | One ASCII character. | `201`. | Section 2 |
| Maximum name | 60 ASCII characters. | `201`. | Section 2 |
| Missing name | Omit `name`. | `422 VALIDATION_ERROR`. | CG-07 |
| Blank name | Empty string, spaces only, or a tab only; separate examples. | `422 VALIDATION_ERROR`. | CG-07 |
| Name too long | 61 ASCII characters after trimming. | `422 VALIDATION_ERROR`. | CG-07 |
| Valid intervals | Try numeric 300, 600 and 900 separately. | `201` for each. | Section 2 |
| Missing interval | Omit `roundIntervalSeconds`. | `422 VALIDATION_ERROR`; no implicit default. | CG-07 |
| Unsupported interval | Try numeric 123, 400 or 1800. | `422 VALIDATION_ERROR`. | CG-07 |
| Wrong interval type | Supply the string `"300"`. | `422 VALIDATION_ERROR`. | CG-07 |
| Broken JSON | Submit an unfinished JSON object as the raw body. | `400 MALFORMED_JSON`. | CG-06 |
| Safe success | Inspect the response from valid creation. | Host token is present; stored hash fields are absent. | CG-03, CG-05 |
| Safe failure | Cause a controlled unexpected failure in the test environment. | `500 INTERNAL_ERROR`; standard safe error fields. | CG-08 |

The field examples can be unit tests of the shared schema once it exists. Keep representative route tests proving the endpoint applies the rules, and HTTP-specific tests for parsing/status/error shape. CG-01, CG-02 and CG-04 need actual database evidence. Avoid claiming a schema test proves a database guarantee.

## 6. Details you and your teammate still need to agree

These details are not fully specified by the existing documents. Do not turn suggestions into required tests without recording the decision in this contract and updating affected design/tests.

| Decision | Why it changes tests |
|---|---|
| Unknown request fields: reject, remove or ignore? | A request with an extra field has no agreed outcome yet. |
| Exact handling of absent bodies, non-object JSON and unsupported content types. | These are distinct boundary cases; the current contract does not completely define their error codes and precedence. |
| Definition of a “character” for Unicode names. | Emojis and combined characters can be counted differently. Use ASCII boundary examples until the rule is explicit. |
| Repeated create requests after a lost response. | No creation idempotency key or replay behavior is defined. Do not assume one lobby or the same token is returned on retry. |
| Join-code collisions and retry limit. | Uniqueness is required, but how many attempts occur and how to exercise exhaustion is not yet agreed. |
| Side effects on validation failure or a partially failed creation. | Proposed guarantee: rejected requests create no lobby, and failed creation leaves no partially created game/session. Agree and test transaction behavior explicitly. |

You can write tests for the settled rules while these decisions are discussed. Stop only the case that depends on an unanswered question.

## 7. How to use this agreement

1. Read one contract rule together and confirm its meaning with an example.
2. The browser uses the agreed inputs and outputs; the API implements the guarantee.
3. Link each test to the rule in the PR description or your evidence notes. You do not need to embed IDs in every test name.
4. If a rule changes, agree on it first, then update this contract, affected design, consumers and tests together.
5. Treat passing tests as evidence for the current contract. Do not silently edit the contract to match an accidental implementation result.

## 8. Other game operations

### `POST /v1/games/:joinCode/teams`

**Caller:** car captain. **Authorization:** none.

```json
{ "name": "Blue Sedan" }
```

**201 response:**

```json
{
  "game": { "id": "…", "name": "Beach convoy", "joinCode": "AB12CD", "status": "LOBBY" },
  "team": { "id": "…", "name": "Blue Sedan", "score": 0, "status": "ACTIVE" },
  "captainToken": "raw-token-returned-once"
}
```

**Acceptance:** rejects a missing game with `404`, a duplicate team name with `409`, and a join after the game starts with `409`.

| Status | Code | Exact condition |
|---|---|---|
| `201` | — | Team and captain token were created in a `LOBBY` game. |
| `400` | `MALFORMED_JSON` | Body is not JSON. |
| `404` | `GAME_NOT_FOUND` | No game has the normalized six-character join code. |
| `409` | `TEAM_NAME_TAKEN` | An existing team in the game has the same case-insensitive normalized name. |
| `409` | `GAME_NOT_JOINABLE` | The game status is not `LOBBY`. |
| `422` | `VALIDATION_ERROR` | Name is missing, blank, or over 60 characters. |
| `500` | `INTERNAL_ERROR` | Token or team persistence fails unexpectedly. |

### `POST /v1/games/:gameId/start`

**Caller:** host. **Authorization:** host token. **Body:** `{ "practice": false }` by default.

**200 response:** `{ "game": { "status": "WAITING", "startedAt": "…", "nextRoundAt": "…" } }`.

**Acceptance:** requires at least two active teams unless the request uses explicit `practice: true`; a non-host receives `403`; a started game receives `409`.

| Status | Code | Exact condition |
|---|---|---|
| `200` | — | Host starts a `LOBBY` game with at least two active teams, or one active team with `practice: true`. |
| `400` | `MALFORMED_JSON` | Body is not JSON. |
| `401` | `UNAUTHENTICATED` | No valid host/captain token is supplied. |
| `403` | `FORBIDDEN` | Token is valid but is not that game's host token. |
| `404` | `GAME_NOT_FOUND` | `gameId` does not exist. |
| `409` | `GAME_ALREADY_STARTED` | Game status is `WAITING` or `COMPLETE`. |
| `422` | `GAME_NOT_READY` | Zero active teams, or fewer than two active teams when `practice` is not exactly `true`. |
| `422` | `VALIDATION_ERROR` | `practice` is present but is not boolean. |
| `500` | `INTERNAL_ERROR` | Start transaction fails unexpectedly. |

### `GET /v1/games/:gameId/snapshot`

**Caller:** host or captain. **Authorization:** token belonging to that game.

**200 response:**

```json
{
	"game": {
		"id": "…",
		"name": "Beach convoy",
		"joinCode": "AB12CD",
		"status": "LOBBY",
		"roundIntervalSeconds": 300,
		"startedAt": null,
		"nextRoundAt": null
	},
	"teams": [{ "id": "…", "name": "Blue Sedan", "score": 0, "status": "ACTIVE" }]
}
```

The lobby slice returns the game fields and active teams above so refresh restores the lobby and its join code. Round fields, the caller's answer and the leaderboard will be added with round delivery; an open round must never expose its answer key or another team's answer. This is not yet the complete in-game snapshot schema.

**Acceptance:** a token from another game receives `403`; a reconnect returns the server’s actual phase; open-round JSON contains no `correctAnswer` text.

| Status | Code | Exact condition |
|---|---|---|
| `200` | — | Host or captain token belongs to the requested game. |
| `401` | `UNAUTHENTICATED` | No valid bearer token. |
| `403` | `FORBIDDEN` | Valid token is for another game. |
| `404` | `GAME_NOT_FOUND` | `gameId` does not exist. |
| `500` | `INTERNAL_ERROR` | Snapshot query fails unexpectedly. |

### `POST /v1/rounds/:roundId/answers`

**Caller:** captain. **Authorization:** captain token.

```json
{ "value": "B" }
```

**200 response:**

```json
{ "answerId": "…", "status": "locked", "roundEndsAt": "2026-08-31T10:05:00Z" }
```

**Acceptance:** the token’s team must belong to the round’s game; choice values must be valid for that question; a second request from the same team returns `409`; a request after the deadline returns `422`; a successful request produces one answer row only.

`value` is a listed choice ID for `MULTIPLE_CHOICE`, a boolean for `TRUE_FALSE`, and a finite JSON number for `ESTIMATE`. The server obtains the question from the round; clients cannot choose or send a question ID.

The captain's team ID comes only from token lookup. Extra request fields are stripped by the delivered answer/leave schemas and cannot choose a team or server time. Invalid answer bodies/values return `422 INVALID_ANSWER_VALUE`. A duplicate is rejected without changing its original value or timestamp, including after reveal; no successful-response replay is promised. A final valid answer may atomically trigger reveal, but this HTTP response still contains only the lock confirmation.

| Status | Code | Exact condition |
|---|---|---|
| `200` | — | An active captain locks one valid answer before the deadline. |
| `400` | `MALFORMED_JSON` | Body is not JSON. |
| `401` | `UNAUTHENTICATED` | No valid bearer token. |
| `403` | `CAPTAIN_REQUIRED` | Token is a host token, not a captain token. |
| `403` | `FORBIDDEN` | Captain's team belongs to a different game from the round. |
| `404` | `ROUND_NOT_FOUND` | `roundId` does not exist. |
| `409` | `TEAM_LEFT` | Captain's team has status `LEFT`. |
| `409` | `ROUND_NOT_OPEN` | Round has already been revealed. |
| `409` | `ANSWER_ALREADY_LOCKED` | The unique answer constraint finds an earlier answer for this team and round. |
| `422` | `ROUND_EXPIRED` | Server time is at or after `ends_at`. |
| `422` | `INVALID_ANSWER_VALUE` | Value type or choice ID is invalid for the round's question. |
| `500` | `INTERNAL_ERROR` | Lock or scoring transaction fails unexpectedly. |

### `POST /v1/games/:gameId/leave`

**Caller:** captain. **Authorization:** captain token.

**200 response:** `{ "team": { "id": "…", "status": "LEFT" } }`.

**Acceptance:** it changes only that captain’s team. An open round retains its original `expected_team_count`; future rounds exclude the left team.

Explicit leave immediately prevents new answers (`409 TEAM_LEFT`). Already locked answers remain eligible for scoring; leaving never removes an expected participant or forces early reveal. Network disconnect alone does not change ACTIVE status. The request body may be omitted or `{}`; invalid non-object bodies return `422 VALIDATION_ERROR`, malformed JSON returns `400 MALFORMED_JSON`.

| Status | Code | Exact condition |
|---|---|---|
| `200` | — | Active captain's team becomes `LEFT`; repeating the same leave is idempotently `200`. |
| `401` | `UNAUTHENTICATED` | No valid bearer token. |
| `403` | `CAPTAIN_REQUIRED` | Token is a host token. |
| `403` | `FORBIDDEN` | Captain's team belongs to another game. |
| `404` | `GAME_NOT_FOUND` | `gameId` does not exist. |
| `409` | `GAME_COMPLETE` | The game is already complete. |
| `500` | `INTERNAL_ERROR` | Team update fails unexpectedly. |

## 9. Live-event contract

The browser opens Socket.IO with `{ auth: { token } }`. The server validates the token and authorizes subscriptions only for its game. The exact snapshot/subscription handshake remains pending section 10; do not implement an uncoordinated fetch-then-subscribe sequence as a settled requirement.

| Event | Recipient | Required payload | Client behavior |
|---|---|---|---|
| `game.updated` | all game members | `game`, `teams` | Replace lobby/team data. |
| `round.started` | all game members | public round only | Replace state with question screen; start display-only countdown. |
| `answer.locked` | submitting captain | `roundId`, `roundEndsAt` | Disable controls and show locked screen. |
| `round.revealed` | all game members | answer, explanation, team results, leaderboard | Replace state with results screen. |
| `game.completed` | all game members | final leaderboard | Show final leaderboard. |

The browser countdown is visual only. It must not locally reveal a round or award points. On disconnect it shows a reconnect status. After reconnect, the resulting view must reflect authoritative state without missing transitions or accepting stale events. Payload fields sufficient to enforce that ordering remain to be specified.
